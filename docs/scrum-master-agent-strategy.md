# Scrum Master Agent 建设策略

> 依据：`docs/scrum-master-products-comparison.md` 的 12 款产品调研。
> 本文回答一个核心问题：**基于这些对比，我该怎么把这个 Agent 做出来、做出差异化？**
> 更新时间：2026-09-06

---

## 一、一句话定位

> **做「站会级的 AI 诊断 + 多角色派生」的 Scrum Master Agent——向上对标 Spinach（仪式自动化），向右对标 Swarmia（团队健康 + 开发者体验），向上兼容 Jellyfish（高管投资视图），但不碰纯财务/资本化。**

一句话记忆：**别人记录会议，我们诊断团队。**

---

## 二、竞争格局与站位（基于调研结论）

调研把市面产品分成三个赛道，且**没有任何一家同时覆盖站会级和高管级**：

```
记录层（A 赛道）          诊断层（本项目的战场）          经营层（C 赛道）
Geekbot/Standuply    →    Scrum Master Agent    ←    Jellyfish/Flow
Range/DailyBot              ↑ 向右补
                       Swarmia/LinearB（B 赛道）
```

**我的站位**：
- 不做「又一个三问记录 bot」（A 赛道红海、护城河低、PLG 卷价格）。
- 不直接做「DORA 仪表盘」（B 赛道强敌环伺，且需要 CI/CD 数据，启动成本高）。
- **做「从每日站会这条最低成本的数据源出发，自动产出诊断级报告，再派生给不同角色」**——这是三个赛道都不占的空位。

**为什么站会是好切入**：站会每天都在发生、数据（字幕/转录）几乎零额外成本、却是团队健康最灵敏的「体温计」；而 DORA/投资分配需要接 CI/CD 与财务系统，冷启动难。先站稳会，再向右、向上扩展。

## 三、目标角色与价值主张

一个 Agent，多套视角。谁用它、得到什么、凭什么留下：

| 角色 | 一句话价值主张 | 对应产物 |
|---|---|---|
| **Scrum Master（首要用户）** | 不用再做会议秘书，专注教练与移除障碍 | 每日诊断报告 + 趋势 + 老化阻塞 + 沉默/过载 + 教练建议 |
| **工程师** | 只看自己相关的条目，不被信息淹没 | 个人视图：我的更新 / 被 owner 的行动项 / 我的 Jira-PR |
| **EM / Lead** | 一眼看团队是否健康、冲刺是否在轨 | health 趋势 + 冲刺进度 + 跨 pod 阻塞 |
| **PO** | 范围有没有失控、阻塞卡在哪 | delivery + 范围变更 + 阻塞 + Jira 状态 |
| **VP / 总监** | 用工程语言讲交付与风险 | 周/月聚合：health / 阻塞 / 缺陷 / 部署趋势 |
| **HR / People Ops** | 捕捉 burnout 早信号 | 沉默趋势、过载趋势、出席率 |

**关键设计原则**：**一份 raw JSON，派生多角色视图**（而非为每个角色各存一份数据）。这是本项目能同时覆盖 A/B/C 三层、且成本远低于任何单一竞品的结构原因。

## 四、报告维度总纲（最终要输出什么）

分三层：**基础记录层 → 诊断层 → 预测/教练层**。诊断与预测是差异化，记录只是载体。

### 4.1 基础记录层（已有，对标 A 赛道）
- 昨日完成 / 今日计划 / 阻塞（三问）
- 决策、行动项（owner + due + 回写 Jira）

### 4.2 诊断层（核心护城河，已建成大半）
| 维度 | 字段 | 竞品对标 | 状态 |
|---|---|---|---|
| 敏捷健康雷达（六维加权） | `health_score` + `health_breakdown` | Swarmia/Waydev 有、但站会级无人做 | ✅ 已有 |
| 会议质量 | `meeting`（聚焦度/跑题/是否绕三大问题） | **市面无同类** | ✅ 已有（独家） |
| 团队情绪（语气识别） | `sentiment` + burnout 预警 | DailyBot/Range 靠自报，我们是语气识别 | ✅ 已有（领先） |
| 反复出现的主题 | `recurring_themes` | Spinach 仅回顾、我们是每日级 | ✅ 已有（领先） |
| 阻塞与依赖 | `blockers_m`（aging + 跨团队/外部分列） | Spinach/Swarmia 弱于此 | ✅ 已有 |
| 团队信号 | `team`（沉默/过载/负载） | Swarmia 有但偏宏观 | ✅ 已有 |
| 流动效率 | `flow`（周期时间/WIP/停滞） | LinearB/Swarmia | ✅ 已有 |

### 4.3 预测 / 教练层（已有 + 待增强）
| 维度 | 字段 | 说明 |
|---|---|---|
| 冲刺预测 | `forecast` | ✅ 已有；**待增强**：前移到站会前出「今日风险清单」 |
| 可行动洞察 | `insights` | ✅ 已有 |
| 教练建议 | `coaching_notes` | ✅ 已有 |
| 分角色执行摘要 | `executive_summary` | ✅ 已有；**待增强**：按 SM/干系人/高管三档话术 |

### 4.4 待补齐维度（调研暴露的差距，按 ROI 排序）
| # | 维度 | 来源 | 数据成本 | 优先级 |
|---|---|---|---|---|
| 1 | 分角色摘要（多受众话术） | Spinach | 低（LLM 改写） | **P1** |
| 2 | 站会前风险清单（阻塞预测） | Spinach | 低（历史 + Jira） | **P1** |
| 3 | DORA 四指标（部署频率/Lead Time/CFR/MTTR） | LinearB/Swarmia | 高（接 CI/CD） | **P2** |
| 4 | 速率 / 冲刺完成率时间序列 | LinearB | 中（聚合 raw JSON） | **P2** |
| 5 | 投资分配（功能/维护/技术债） | Jellyfish/Swarmia | 中（Jira label 规则） | **P2** |
| 6 | 团队 DX 调研（主动问卷 × 指标交叉） | Swarmia | 中 | **P3** |
| 7 | working agreements 告警（PR 大小/评审周转） | Swarmia | 中 | **P3** |
| 8 | 站会主持辅助（计时/随机发言） | Spinach | 低 | **P4** |

## 五、差异化护城河（3 个独家点）

1. **每日站会自动诊断**：市面上没有人从「每日站会」自动产出健康雷达 + 会议质量 + 情绪 + 反复主题。别人要么做记录（A 类）、要么做周期级指标（B 类），中间「每日诊断」是空的。
2. **情绪从语气识别，而非自报**：DailyBot/Range 靠成员主动填 mood（有社交压力、易失真）；我们直接从字幕措辞语气识别，更客观、零负担。
3. **一份数据派生多角色**：结构上能同时服务 SM 到 VP，边际成本趋近于零。这是 B/C 类重平台做不到的灵活性。

**护城河要持续加厚，靠两件事**：诊断维度持续领先 + 多角色视图持续下沉（把数据「讲成各角色听得懂的话」）。

## 六、分阶段路线图（修订版，含竞品对标）

在现有 P0–P5 基础上，把竞品借鉴点显式塞进阶段：

| 阶段 | 目标 | 竞品借鉴点 | 状态 |
|---|---|---|---|
| **P0** | 手动投喂转录 → JSON → 本地 HTML（六维健康雷达 + 诊断维度） | — | ✅ 已完成 |
| **P1** | 接 GitHub MCP 发布 + **分角色摘要 + 站会前风险清单** | Spinach（recap/预测） | 🔄 摘要已有，风险清单待加 |
| **P2** | 接 Jira MCP + **DORA 四指标 + 投资分配 + 速率时间序列** | LinearB/Swarmia/Jellyfish | 🔄 Jira 已接，指标待加 |

| **P5** | 多期聚合面板（健康雷达趋势/冲刺预测历史/情绪趋势） | LinearB | 待做 |

## 七、技术架构演进要点

当前架构（`ingest → extract → enrich → trends → render → publish`，五触点全链路 LLM）已经够用，按阶段做三处演进：

1. **P1 角色视图层**：在 `render` 之后加一个 `view` 层——同一份 raw JSON，按 persona 套不同模板（`me/manager/po/leadership/cross-team/hr`）。**不改数据模型，只加视图模板**（架构图里 `GH → FE` 之前插入 `view`）。
2. **P2 指标层**：新增 `metrics` 阶段或扩展 `enrich`，从 CI/CD（GitHub Actions / 部署系统）拉 DORA 四指标；Jira label 规则算投资分配。**保持「LLM 失败不阻断」的降级原则不变**。
3. **P5 聚合层**：现有 `trends` 只做相邻两期对比，升级为「读多期 raw JSON 的聚合器」，产出时间序列（health/velocity/sentiment 趋势）。

**架构铁律（沿用已有共识）**：
- LLM 全链路可降级，LLM 挂了绝不阻断出报告。
- GitHub 仓库即数据库，不引入额外 DB。
- 草稿 → 人工确认 → 发布，写操作默认关闭（Jira 自动建单是高风险动作）。

## 八、北极星指标与成功度量

**产品北极星**：每周被 SM 主动打开并据以行动的「诊断报告数」（而非生成份数）。

**过程指标**（对齐竞品建议的 KPI）：
- 采用前后对比：冲刺完成率（sprint completion rate）
- 周期时间（cycle time）
- 会议耗时（time in meetings）——验证「减负」是否成立
- 阻塞平均存续时长（aging days）——验证「诊断」是否带来行动

**一句话验收标准**：SM 每周省下 N 小时会议秘书工作，且阻塞平均老化天数下降——两个都做到，才算立住了。

## 九、明确「不做什么」（反定位）

| 不做 | 原因 |
|---|---|
| 纯财务/研发资本化 | Jellyfish 的红海，需 CFO 级合规，冷启动重 |
| 做 DORA 仪表盘但不做诊断 | B 赛道内卷，无差异化 |
| 追求「三问记录」的极致表单化 | A 赛道无护城河 |
| 用 velocity 当绩效打分 | 古德哈特定律，团队会刷点数，反噬信任 |
| 把 Agent 吹成「替代 Scrum Master」 | SM 的教练/冲突/信任是人的活，Agent 只替行政 |

**人机边界**（来自调研里 Scrum 从业者的共识，务必写进产品价值观）：
> AI 接管的是「过程/行政」——摘要、行动项、指标、风险预警；**人的部分——建立信任、教练、化解冲突、对齐干系人——绝不自动化和越界**。产品叙事永远用「赋能 SM」而非「替代 SM」。

## 十、立即行动清单（接下来 30 天）

1. **P1**：实现「分角色执行摘要」（SM / 干系人 / 高管 三档话术），复用现有 `executive_summary` 字段，加 persona 参数即可。
2. **P1**：实现「站会前风险清单」——用上一期 raw JSON + Jira 老化阻塞，在 `generate` 前置一个 `pre-risks` 输出。
3. **P2 启动**：接 GitHub Actions 数据，先落地 DORA 里的「部署频率 + Lead Time」两个最容易的指标（CFR/MTTR 依赖事故系统，后置）。
4. **角色视图**：优先做 SM 自己的趋势视图（他是唯一会主动看的人），其余角色视图做得越短越好。
5. **度量埋点**：在报告里记录「SM 打开/确认/据以行动」的轻量信号，为北极星指标攒数据。
